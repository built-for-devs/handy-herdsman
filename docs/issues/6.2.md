## Summary
For protocol (sync) bookings, schedule all three visits up front and validate the V3 window against working hours, existing bookings, buffer, and distance.

## Spec references
- §3, §5.5, §10b. Depends on **1.1**.

## Requirements
- Using the 1.1 service, compute V2/V3 for candidate V1 dates; validate downstream windows.
- Offer only viable V1 dates whose downstream windows all work.

## Acceptance criteria
- [ ] All three visits scheduled up front; V3 window validated against working hours (`availability_rules`), existing bookings, inter-appointment buffer, and distance (§3, §5.5).
- [ ] Out-of-range clients: the V3 window must accommodate drive time (§3).
- [ ] **If no valid V1 date exists within `config('protocol.search_horizon_days')`, say so EXPLICITLY and offer the next viable dates beyond it** — never fail silently or return an empty picker (§10b).
- [ ] Windows use absolute-duration, DST-safe math (1.1).

## Mobile behavior
Show only viable dates; explain window reasoning simply; big date targets.

## Config over code
Horizon, working hours, buffer from config/`availability_rules`.

## Tests
- Fully-booked week → offers later viable dates with an explicit message (no empty picker).
- Candidate V1 whose V3 falls outside hours is excluded.

## Definition of done
Up-front 3-visit scheduling with full validation; explicit no-date messaging.
