## Summary
The shared, tested service class that computes the CIDR 10-day sync windows. It powers the public calculator (2.5) and the booking scheduler (6.2). **A wrong assumption here causes failed breedings, not bugs** — this is the highest-consequence code in the system.

## Spec references
- §3 (The AI protocol) — CIDR 10-day sync, three visits.
- §10b (Animal type; Timing math) — binding.

## Requirements
- Read all constants from `config/protocol.php` (`v1_to_v2_days`, `windows.cow` = 60–66h, `windows.heifer` = 52–56h, `timezone` = America/Chicago). No literals.
- Given a proposed Visit 1 timestamp + animal type, output: Visit 2 time, and the Visit 3 window (start/end) + recommended time.
- Persist to `protocols` (`visit1_at`, `visit2_at`, `visit3_window_start`, `visit3_window_end`).

## Acceptance criteria
- [ ] V1 → V2 = exactly **7 days** (absolute duration).
- [ ] V3 window = **60–66h (cow)** / **52–56h (heifer)** measured from V2's timestamp.
- [ ] Recommended AI time = **window midpoint** (cow ≈63h, heifer ≈54h); full window returned as the acceptable range.
- [ ] All timestamps **stored in UTC**, computed and **displayed in America/Chicago**.
- [ ] All hour/day offsets added as **absolute durations, never calendar arithmetic** — a DST boundary must not shift a window.
- [ ] Timing constants come from config, not literals.

## Config over code
Timing constants live in `config/protocol.php` — one edit if guidance changes.

## Tests (mandatory, heavy)
- [ ] Cow window = V2+60h..V2+66h; heifer = V2+52h..V2+56h; midpoints correct.
- [ ] V1→V2 exactly 7×24h.
- [ ] **DST spring-forward** crossing (America/Chicago) in both the V1→V2 leg and the V2→V3 leg — window is unchanged in absolute hours.
- [ ] **DST fall-back** crossing, same.
- [ ] A V2 near midnight produces a correctly-dated V3 window in Chicago local display.

## Definition of done
Cites spec; UTC/absolute-duration rules enforced; heavy tests incl. both DST directions pass.
