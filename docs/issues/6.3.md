## Summary
The availability the scheduler reads, the Sunday rule, and blackout dates with a client re-book flow.

## Spec references
- §7, §10b (Scheduler & availability)

## Requirements
- Working hours, max visits/day, buffer from `availability_rules`; blackouts from `blackout_dates`.

## Acceptance criteria
- [ ] Working hours, max visits/day, and inter-appointment buffer are **config values the scheduler reads** — not hardcoded; travel time between appointments is accounted for (§7, §10b).
- [ ] **No Sunday-morning appointments, ever. Sundays off by default** — but **on-call emergencies are always allowed** (bypass availability entirely) (§10b).
- [ ] Blackout dates block scheduling; **emergencies still bypass** (§10b).
- [ ] When a blackout is added **over existing bookings**: notify affected clients, propose alternative slots that still satisfy protocol timing, and ask them to confirm (§10b).
- [ ] **A protocol already past Visit 1 cannot simply be moved** (V2/V3 windows physiologically fixed) → surfaces to Jeff as a **conflict requiring a manual decision**, not auto-rebooking (§10b).

## Mobile behavior
Blackout add is a quick date-range picker; conflict list is scannable.

## Config over code
Availability + blackouts are editable data.

## Tests
- No Sunday-morning slot offered; emergency bypasses.
- Blackout over bookings notifies clients + proposes alternatives.
- Post-V1 protocol surfaces as manual conflict, not auto-moved.

## Definition of done
Config-driven availability, Sunday rule, blackout re-book flow, post-V1 manual conflict.
