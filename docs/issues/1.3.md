TITLE: 1.3 — Visit-2-late recomputation
MILESTONE: M1 — Protocol timing engine
LABELS: devin,timing
---
## Summary
When Visit 2 runs late, Visit 3 must shift with it — automatically. This is the common real-world case.

## Spec references
- §10b (Timing math) — binding.

## Requirements
- On V2 completion, recompute V3 from `visit_completions.completed_at` (the actual timestamp), never the planned one.

## Acceptance criteria
- [ ] V3 window is **always recomputed from Visit 2's actual completed timestamp**.
- [ ] If V2 runs 2h late, V3 shifts 2h.
- [ ] Recompute happens **automatically** on V2 completion.
- [ ] Any resulting conflict (outside working hours / collides with another V3 window) is **flagged and surfaced/notified**, not silently accepted.

## Tests
- [ ] V2 completed on-time vs +2h vs −1h → V3 shifts by exactly that delta.
- [ ] Recompute that pushes V3 outside working hours raises a flagged conflict.

## Definition of done
Automatic recompute on V2 completion, with conflict flagging; tested.
