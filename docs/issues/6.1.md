## Summary
The core booking flow. Service `type` routes the path; clients book immediately, with first-timers provisional pending review.

## Spec references
- §5.5 (Booking). Depends on **M1** (timing) and **M3** (clients/status).

## Requirements
- Choose a `service`; flow follows `services.type` = protocol | oncall | standard.
- Create `bookings` with status provisional/confirmed/declined; `requires_review`, `is_oncall`.

## Acceptance criteria
- [ ] Service `type` routes the flow: **protocol** (3-visit sync scheduler, 6.2), **oncall** (expedited, 6.5), **standard** (single-visit date request) (§5.2, §5.5).
- [ ] **Book immediately** — no pre-approval to make an appointment (§4).
- [ ] **First-time appointments are provisional pending staff review** (24h SLA); provisional status is clearly visible to the client (§10b).
- [ ] **Established (`active`) clients self-confirm** subject to timing/distance validation — no manual gate (§4, 3.2).
- [ ] Bookings are team-scoped.

## Mobile behavior
Service picker with big cards; minimal-typing flow; clear provisional/confirmed status.

## Config over code
Service definitions from `services`; status rules from 3.2.

## Tests
- New client booking → provisional + requires_review.
- Active client standard booking → self-confirms after validation.
- Type routes to the correct sub-flow.

## Definition of done
Type-routed booking; immediate booking; provisional-vs-self-confirm per status.
